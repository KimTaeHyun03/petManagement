# 역할별 예상 질문 대비 (Q&A)

> 심사위원이 담당자별로 후벼팔 질문 + 모범 답변.
> **PPT와 별도 문서.** 각자 본인 섹션을 외워두고, 데모 중 들통날 수 있는 spec↔코드 차이는 ⚠로 표시.
> 답변 원칙: **모르면 "현재는 X, 향후 Y 예정"으로 정직하게.** 코드와 다른 spec을 외워 읊지 말 것.

## 공통 (누구나 받을 수 있음)

**Q. 기존 반려동물 앱(펫프렌즈, 동물병원 앱 등)과 뭐가 다른가요?**
> 기존 서비스는 기록을 일일이 폼으로 입력해야 하고 단순 저장에 그칩니다. 저희는 ①OCR로 사진 한 장이면 입력이 끝나고, ②누적 기록을 챗봇이 컨텍스트로 받아 상담하며, ③의료 정보 신뢰성을 1차 출처 교차검증으로 확보한 점이 다릅니다.

**Q. AI가 잘못된 의료 정보를 주면 책임은 누가 지나요?**
> 그래서 처음부터 AI 진단·처방을 금지하도록 설계했습니다. 챗봇은 일반 건강 정보만 제공하고 모든 답변에 면책 고지를 붙이며, 응급 증상이 언급되면 즉시 병원 방문을 권장합니다. 데이터도 학회·정부 1차 출처를 교차검증한 것만 씁니다.

**Q. 실제 사용자 테스트는 했나요? / 정확도 평가는?**
> (정직하게) 현재는 팀 내부 계정으로 기능 검증을 했고, 사용자 테스트와 OCR 정확도 정량 평가는 다음 단계 계획입니다. — *없는 데이터를 지어내지 말 것.*

**Q. 강아지·고양이 외 다른 동물은요?**
> 가장 많이 키우는 두 종에 우선 집중했습니다. 데이터 모델은 `species` 필드로 확장 가능하게 설계돼 있어, 마스터 데이터만 추가하면 종을 늘릴 수 있습니다.

## 김태현 (총괄) — 회원가입/로그인, 펫 등록, 챗봇

### 인증 ⚠ (가장 주의할 구간)

**Q. 로그인 인증은 어떻게 유지하나요? 토큰 만료/재발급 정책은?**
> ⚠ **코드 기준으로 답할 것.** "현재 1차 구현은 **Access 토큰 단독**이고, httpOnly·Secure 쿠키로 전달하며 기본 만료는 2시간입니다. 운영 전환 시 Refresh Token Rotation을 도입하고 Access TTL을 더 짧게 가져갈 계획입니다."
> — ❌ "Refresh 14일 Rotation 합니다"라고 답하면 안 됨 (PLAN 문서엔 그렇게 적혀 있지만 코드는 미구현)

**Q. 비밀번호는 어떻게 저장하나요?**
> **Argon2id**로 해시합니다. (PLAN 본문엔 bcrypt로 적혀 있지만 실제로는 더 강한 Argon2id를 썼습니다.) 추가로 가입 시 Pwned Passwords로 유출 이력을 검사하고, 로그인 시 더미 해시 비교로 타이밍 공격을 막습니다.

**Q. 다른 사람이 내 반려동물 정보를 보는 걸 어떻게 막나요?**
> 모든 펫 데이터는 `pet_id`로 분리되고, 모든 펫 API에서 "요청한 사용자가 이 펫의 주인인지"를 검증합니다. 챗봇 컨텍스트도 `loadPetContext(petId, userId)`에서 소유권을 확인해 다른 사용자 데이터가 섞이지 않습니다.

### 챗봇

**Q. 챗봇은 그냥 ChatGPT에 물어보는 거랑 뭐가 다른가요?**
> 핵심 차이는 **컨텍스트 주입**입니다. 일반 GPT는 일반론만 답하지만, 저희는 그 펫의 실제 체중 추이·접종 이력·성분표 스캔·표준 백신 일정을 메시지로 주입해서 '우리 아이' 맞춤 답을 만듭니다. RAG 방식입니다.

**Q. 어떤 모델을 쓰나요? 비용은?**
> OpenAI `gpt-4o-mini`를 씁니다. 경량 모델이라 응답이 빠르고 비용 효율이 좋아 상담 챗봇 용도에 적합합니다. (temperature 0.5, 응답 800토큰 제한)

**Q. GPT가 환각(없는 사실)을 답하면요?**
> 그 문제를 실제로 겪었습니다. GPT가 백신 이름을 임의 약자로 바꾸길래, 시스템 프롬프트에 'DB 컨텍스트의 명칭·시기를 그대로 쓰라'고 강제하고 표준 일정을 직접 주입해 교정했습니다. 또 모든 답변에 'DB 자료를 최우선'이라는 규칙을 넣었습니다.

**Q. 대화 기록은 어떻게 관리되나요?**
> `ChatLog` 테이블에 user/assistant 메시지를 저장하고, assistant 답변에는 그때 사용한 컨텍스트를 `context_snapshot_json`으로 함께 저장해 나중에 감사·재현이 가능합니다.

## 김기연 — 체중 관리(급변 알림), 통합 타임라인·대시보드

**Q. 체중 '급변' 기준은 뭔가요? 왜 10%인가요?**
> 직전 기록 대비 ±10% 이상 변동을 급변으로 잡습니다(PLAN 4.3). 단기간 10% 체중 변화는 수의학적으로 유의미한 신호로 보는 기준을 따랐고, 정상 추세에는 알림을 안 보내 알림 피로를 줄였습니다.

**Q. 정상/과체중/저체중 판정 근거는?**
> 품종·연령별 표준 체중표(`StandardWeight` 마스터)와 비교합니다. 이 표는 KASA·AVMA 같은 1차 출처를 기준으로 만들었습니다.

**Q. 급변 알림은 어떤 채널로 가나요?**
> 현재는 **이메일**(nodemailer)로 발송하고 DB에 기록합니다. 기록 저장과 별도로 비동기(fire-and-forget) 처리해서 메일 실패가 API 응답을 막지 않게 했고, `weight_alerts` 테이블의 UNIQUE 제약으로 중복 발송을 막습니다.
> ⚠ PLAN 표엔 "Push/Email"로 적혀 있지만 **웹 푸시는 미구현, 현재 이메일만**입니다.

**Q. 타임라인은 어떻게 통합하나요?**
> 체중·접종·OCR 스캔 이벤트를 시간축으로 병합해 한 화면에 보여줍니다. 카테고리·날짜 필터를 제공하고, 대시보드 수치는 더미가 아니라 실제 데이터를 집계한 값입니다(커밋 `a823cf2`).

**Q. 타임라인을 가장 마지막에 만든 이유는?**
> 타임라인은 다른 모든 기능의 기록을 모아 보여주는 화면이라, 체중·접종·OCR이 먼저 구현돼야 의미가 있어 마지막에 통합했습니다.

## 장윤서 — OCR, 위험음식 검색·알러지 매칭

**Q. OCR 엔진은 뭘 썼나요? 왜 그걸 골랐나요?**
> **Naver CLOVA OCR**(General V2)을 썼습니다. 한글 인식 정확도가 좋고, 영수증·성분표 같은 한국어 문서에 강하며, API 연동이 간단해 선택했습니다.
> ⚠ PLAN엔 "Google Vision/Tesseract/Clova 비교 후 선정 예정"으로 적혀 있는데, 비교 끝에 **CLOVA로 확정**했다고 답하면 됩니다.

**Q. 영수증인지 성분표인지 어떻게 구분하나요?**
> 추출 텍스트에서 키워드 점수를 셉니다. '원재료·성분·조단백질'이 많으면 성분표, '결제·동물병원·접종'이 많으면 영수증으로 분류하고, 사용자가 화면에서 다시 확정할 수 있게 했습니다.

**Q. OCR이 틀리면요? 위험성분을 놓치거나 잘못 잡으면?**
> 그래서 자동 저장을 안 합니다. OCR 결과를 사용자가 확인하고 확정한 뒤에 저장합니다. 또 위험성분은 ASPCA 23개 목록과 키워드 매칭하고, 알러지는 그 펫의 등록 정보와 매칭해 이중으로 확인합니다.

**Q. 위험음식 목록의 출처는?**
> ASPCA(미국 동물학대방지협회) 자료를 1차 출처로 쓰고, 머크 수의 매뉴얼·VCA 등으로 교차검증한 항목만 등재했습니다.

**Q. 매칭이 단순 키워드 포함이면 오탐이 많지 않나요?**
> (정직하게) 현재는 키워드 매칭 기반이고, 오탐을 줄이기 위해 위험성분은 사용자에게 '참고용·진단 아님'을 명시해 노출합니다. 정밀 매칭(동의어·표기 변형 사전)은 개선 과제입니다.

## 김찬영 — 예방접종, 영수증 OCR 자동기록, DB·배포

**Q. 다음 접종일은 어떻게 계산하나요?**
> 접종 완료를 입력하면 백신 마스터(`Vaccine`)의 권장 시기·차수·간격을 기준으로 다음 권장일을 자동 계산하고 알림을 예약합니다. 강아지는 6주~16주 다회차, 고양이는 8주~16주, 그리고 광견병 같은 부스터까지 처리합니다.

**Q. 접종 알림은 언제, 어떻게 발송되나요?**
> `node-cron` 스케줄러가 **매일 KST 오전 9시**에 돌면서 D-7·D-1·당일에 해당하는 펫을 찾아 **이메일**을 보냅니다. `notification_log`에 발송 기록을 남겨 같은 날 중복 발송을 막습니다.

**Q. 영수증 OCR로 접종을 자동 기록한다는데, 잘못 기록되면?**
> 영수증에서 결제일·백신명·차수를 뽑아 접종 후보를 만들지만, 바로 저장하지 않고 사용자 확정 화면을 거칩니다. 확정된 기록은 `source: ocr`로 표시해 수동 입력과 구분합니다.

**Q. 광견병 같은 법적 의무 백신은 어떻게 다루나요?**
> 백신 마스터에 `mandatory` 플래그를 둬서 법적 의무 백신을 구분하고, 미접종 시 강조 톤으로 경고합니다. 광견병은 생후 3개월 이상 의무이고 미접종 시 과태료 대상임을 안내합니다.

**Q. DB는 뭘 쓰고 어떻게 운영하나요?**
> **AWS RDS PostgreSQL**입니다. 마이그레이션을 13개 파일로 버전 관리하고 `npm run migrate` 러너로 적용합니다. 운영 데이터와 별도로 위험음식·백신·표준체중 마스터를 둡니다.

**Q. 배포 구조는?**
> 프론트 React 빌드는 S3, 백엔드 Express는 EC2, DB는 RDS, OCR 원본 이미지는 S3에 보관합니다. S3 인증은 EC2 IAM Role 방식을 지원합니다(커밋 `4f96bce`).

## ⚠ 절대 틀리면 안 되는 spec↔코드 차이 (전원 숙지)

| 항목 | PLAN/문서에 적힌 것 | **실제 코드 (이렇게 답할 것)** |
|---|---|---|
| 인증 | Refresh 14일 Rotation | **Access-only JWT, httpOnly 2h** (Refresh는 향후) |
| 비밀번호 | bcrypt | **Argon2id** |
| OCR 엔진 | "선정 예정" | **Naver CLOVA OCR** |
| 챗봇 모델 | "OpenAI API" | **gpt-4o-mini** |
| 알림 채널 | Push / Email | **이메일만** (웹 푸시 미구현) |

> 데모 중 또는 Q&A에서 위 표의 왼쪽(문서값)을 말하면 코드와 어긋나 그 자리에서 깨진다.
> 항상 **오른쪽(코드값)** 으로 답하고, 차이가 나는 이유는 "문서는 설계 목표였고 1차 구현에서 X를 택했다"로 설명한다.
