# PawCare 기술 차별점 정리

> 심사위원이 "그래서 기술적으로 뭐가 다른데?"라고 물을 때 답할 4가지.
> **모두 실제 코드 기준(as-built)** 으로 작성. 문서 spec과 다른 부분은 ⚠로 표시.

---

## 차별점 1 — 펫 단위 RAG 챗봇 (단순 GPT 래퍼가 아님)

**무엇이 다른가**
일반 챗봇은 "강아지 체중이 줄면 어떡하죠?" 같은 *일반론*만 답한다.
PawCare 챗봇은 **이 펫의 실제 DB 기록**을 컨텍스트로 주입해서 *우리 아이 맞춤* 답을 한다.

**어떻게 구현했나** (`chatbot.service.ts`)
- 모델: **OpenAI `gpt-4o-mini`** (temperature 0.5, max_tokens 800)
- 3단 메시지 구조:
  1. `system` — 시스템 프롬프트 (진단 금지 + 면책 고지 규칙)
  2. `system` — **펫 컨텍스트** (아래 데이터를 실시간 조회해 조립)
  3. `user` — 사용자 질문
- 주입하는 컨텍스트:
  - 프로필 (종·품종·생일·**알러지**)
  - **체중 변화 추이** (최근 기록 전체를 오래된→최신 순으로 + 구간 증감량 계산)
  - **완료한 예방접종 이력** + 예정된 접종
  - 최근 성분표 스캔 결과 (위험성분 매칭 포함)
  - **종별 표준 예방접종 일정** (마스터 DB)

**까다로웠던 점 → 해결**
- GPT가 백신명을 `DHPP`/`DHPPi`처럼 임의 약자로 바꿔 답하는 문제
  → 시스템 프롬프트에 *"반드시 컨텍스트의 명칭과 시기를 그대로 사용"* 명시 + 표준 일정을 컨텍스트로 직접 주입 (최근 커밋 `c6cd99c`)
- 체중 질문에 최신값 하나만 답하던 문제
  → 추이 전체를 시간순으로 주입하고 증감 흐름을 설명하도록 프롬프트 보강 (`6b98905`)

**보안 포인트**
- `loadPetContext(petId, userId)` 가 **사용자-펫 소유권을 검증** → 남의 펫 데이터 누출 차단
- 응답 시점 컨텍스트를 `ChatLog.context_snapshot_json` 에 저장 → **감사·재현 가능**

## 차별점 2 — OCR 자동 기록 (입력 부담 제거 + 오인식 방어)

**무엇이 다른가**
경쟁 서비스는 체중·접종·음식을 *각각 폼으로* 입력해야 한다.
PawCare는 **사진 한 장**이면 OCR이 분류·매칭·기록한다.

**어떻게 구현했나** (`ocr.service.ts`)
- OCR 엔진: **Naver CLOVA OCR (General V2)** — multipart/form-data로 이미지 전송, `X-OCR-SECRET` 인증
  - ⚠ PLAN 7절은 "선정 예정"이라 적혀 있으나 **실제로는 CLOVA 채택**
- 문서 자동 분류: 추출 텍스트의 키워드 점수로 성분표 vs 영수증 판정
  - 성분표 키워드: `원재료`, `성분`, `조단백질`, `조지방`, `영양성분` …
  - 영수증 키워드: `결제`, `동물병원`, `백신`, `접종`, `진료` …
- 레이아웃 부분 보존: CLOVA의 `lineBreak` 플래그로 줄 구분 → "제품명" 자동 추출
- 분기:
  - 성분표 → 위험성분 DB + 펫 알러지 **이중 매칭** → 즉시 경고 카드
  - 영수증 → 접종 후보 생성 → **사용자 확정 후** VaccinationRecord 저장

**까다로웠던 점 → 해결**
- OCR이 틀리면 **잘못된 의료 기록**이 남는다
  → 자동 저장 금지. 항상 *"사용자 확정 후 저장"* 단계를 거침 (PLAN 4.4)
- 한글 패키지의 "제 품 명"처럼 글자 사이 공백
  → 정규식에 `\s*`를 넣어 띄어쓰기 변형까지 인식

## 차별점 3 — 의료 도메인 안전장치 (캡스톤 차별 포인트)

**왜 중요한가**
의료 인접 서비스에서 **오정보 = 동물의 건강 위험**. "기능을 많이 넣었다"가 아니라 *"틀린 정보를 안 주도록 설계했다"* 가 핵심.

**4중 안전장치**
1. **AI 진단 금지** — 챗봇 시스템 프롬프트에 *"진단·처방·투약 지시 절대 금지, 일반 정보만"* 하드코딩
2. **면책 고지 상시 노출** — 모든 챗봇 답변 끝에 *"본 정보는 참고용이며, 정확한 진단은 수의사에게"* 강제. 응급 증상(호흡곤란·경련·출혈) 언급 시 즉시 병원 방문 권장
3. **1차 출처 교차검증** — 위험음식(ASPCA)·백신(KASA·검역본부)·표준체중(KASA·AVMA) 마스터 데이터는 **1차 출처 + 2개 이상 교차검증** 통과분만 등재. 블로그·요약글 인용 금지
4. **OCR 사용자 확정** — 의료 기록은 자동 저장하지 않고 사람이 확인 후 저장

**의도적 범위 제외 = 책임 회피가 아니라 설계 결정**
- 증상 입력 → 질환 매핑 (의료 진단 책임 영역이라 제외)
- 위험도 종합 점수 엔진 (근거 불충분한 점수화는 오히려 오해 유발 → MVP 제외)

## 차별점 4 — 인증·인가 보안 설계

> ⚠ **발표·Q&A 주의**: PLAN 4.1 / workflow 6절은 "Refresh 14일 Rotation"이라 적혀 있으나
> **실제 1차 구현은 Access-only**다. 아래는 **코드 기준**이다.

**실제 구현** (`auth.service.ts`, `auth.controller.ts`, `utils/password.js`)
- **Argon2id** 비밀번호 해시 (⚠ PLAN 본문의 "bcrypt"보다 강한 최신 표준 — `argon2` 패키지)
- **Pwned Passwords 검사** — 가입 시 유출된 비밀번호 차단 (prod에서 강제 활성)
- **타이밍 공격 방어** — 로그인 시 사용자가 없어도 더미 해시로 비교해 응답시간 일정화
- **JWT Access 토큰** — `httpOnly` + `Secure` 쿠키 전달 (기본 만료 2h)
- **Rate Limit** — `express-rate-limit`로 로그인 무차별 대입 차단
- **펫 소유권 검증** — 모든 펫 라우트에서 사용자-펫 권한 확인

**현재 한계 (정직하게 말할 것)**
- Refresh Token Rotation은 **미구현** (`TODO.md` 트래커). 현재는 Access-only 2h.
- → "운영 전환 시 Refresh Rotation 도입 + Access TTL 단축 예정"으로 프레이밍
